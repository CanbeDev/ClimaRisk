ClimRisk — Follow-up items (not fixed, judgment calls)
Captured: 2026-09-05
Context: found during a code review pass after fixing the /hazards hardcoded-ZAF bug
and the GDACSClient retry-bypass bug (both of those ARE fixed already — this list is
only the items that were flagged but deliberately left alone pending your decision).

1. /assets has no country scoping
   File: app/routes/assets.py
   The /hazards endpoint now filters by settings.gdacs_country_filter (fixed), but
   /assets returns every row in the table with no iso3 filter at all. Harmless today
   if your asset data is ZAF-only, but inconsistent with /hazards, and will silently
   return other countries' assets if this table ever holds multi-country data.
   Possible fix: add `WHERE iso3 = %s` using the same settings.gdacs_country_filter,
   mirroring hazards.py.

2. idx_hazard_events_zaf_fromdate migration index is still ZAF-hardcoded
   RESOLVED in migration 009 (global-events pass): the partial index is dropped and
   replaced with a plain (iso3, from_date DESC) composite, since global ingestion made
   "a second country is actually configured" true in effect.

3. upsert_event's conflict-resolution only guards `centroid` against stale overwrites
   File: app/db/repository.py (HazardRepository.upsert_event, ON CONFLICT clause)
   On re-ingestion, `centroid` is only overwritten if the incoming row's date_modified
   is newer (or either side is null) — a deliberate staleness guard. Every other field
   (alert_level, severity_value, severity_text, is_current, title, description, etc.)
   is unconditionally overwritten by whatever the latest run saw, with no equivalent
   staleness check. Probably fine in practice (GDACS episode data rarely regresses),
   but if backfill and realtime ever race on the same episode, only centroid is
   protected from going backwards.
   Possible fix: extend the same CASE/date_modified guard to the other mutable fields,
   or confirm this asymmetry is intentional and document it.

4. Test suite triggers the full app lifespan (DB pool + APScheduler)
   File: tests/test_exposure.py (client fixture, `with TestClient(app) as test_client`)
   FastAPI's lifespan runs on TestClient startup, which calls init_pool() and
   start_scheduler() using whatever .env is active when pytest runs. If
   SCHEDULER_ENABLED=true (the default), a real background scheduler thread starts
   during test runs. Low risk in practice — the realtime/polygon jobs are on 2h/6h
   intervals so they won't fire during a normal test run — but pytest isn't fully
   hermetic here, and this could surprise someone running tests against a shared or
   production-like .env.
   Possible fix: override SCHEDULER_ENABLED=false (and maybe point at a disposable
   test DB) via a conftest.py fixture or environment override before importing app.

5. Polygon enrichment under global ingestion volume  (flagged 2026-09-08, not fixed)
   File: app/db/repository.py (fetch_pending_polygons) + app/ingestion/polygons.py
   The polygon job still only enriches country-scoped events — its query keeps
   `WHERE (iso3 = %s OR %s = ANY(affected_countries)) AND footprint IS NULL AND
   geometry_url IS NOT NULL` — so the *work per run* does NOT grow with global
   ingestion; only ZAF-affecting events get a geometry fetch. Two things still to
   watch once real global data lands:
   (a) idx_hazard_events_footprint_pending is a partial index on (last_seen_at)
       WHERE footprint IS NULL AND geometry_url IS NOT NULL, with no country column.
       With many non-ZAF pending rows in it, the planner has to BitmapOr the iso3 /
       affected_countries indexes and post-filter; confirm EXPLAIN still picks a
       sane plan for the LIMIT 100 query rather than scanning the whole partial index.
   (b) If polygon enrichment is ever made global too, the 6h cadence + GDACS's own
       rate limits (0.5s polite delay per request) won't keep up with a worldwide
       pending backlog — it would need to prioritize ZAF / near-ZAF events first,
       or run a tighter interval for a priority sub-set.
